1. Introduction

The [native-app-payment-handler] API defines an abstract functional model, the native payment app provider model, through which user agents can interact with native payment apps in order to treat them as native-app payment handlers that are accessible via the [payment-request] API.

This document describes one concrete implementation of that model, the Android payment app provider, which defines how a user agent running on the Android Operating System can interact with other applications on the same device that want to act as payment apps.

2. Android Payment App Provider

The Android Payment App Provider is a native payment app provider that defines how a user agent can access Android native payment apps. The necessary functionality is built on top of standard Android OS concepts for cross-application communication and collaboration:

  • AndroidManifest.xml

  • Intents

  • Services

2.1. Payment app AndroidManifest.xml

In order to be visible to the user agent, the Android payment app defines the following concepts in their AndroidManifest.xml file:

  1. An optional "is ready to pay" Android service, which the user agent will bind to and call when determining if the app can handle a PaymentRequest.

  2. A mandatory "pay" Android activity, which will receive an intent when the user agent invokes the app.

2.1.1. The IS_READY_TO_PAY service

The IS_READY_TO_PAY service receives calls from the user agent to determine if the app can handle a PaymentRequest. If present, it must be exported and have an intent filter with an org.chromium.intent.action.IS_READY_TO_PAY action:

<service
    ...
    android:exported="true">
  <intent-filter>
    <action android:name="org.chromium.intent.action.IS_READY_TO_PAY" />
  </intent-filter>
</service>

2.1.2. The PAY activity

The PAY activity will receive an intent from the user agent when the user agent invokes the app to handle a PaymentRequest. It must be exported and have:

  • An intent filter with an org.chromium.intent.action.PAY action

  • An org.chromium.default_payment_method_name <meta-data> tag.

  • Optionally, an org.chromium.payment_method_names <meta-data> tag.

The org.chromium.default_payment_method_name tag must be a string representing a valid url-based payment method identifier and is used for § 2.4 Claiming a method URL.

<activity
    ...
     android:exported="true">
  <intent-filter>
    <action android:name="org.chromium.intent.action.PAY" />
  </intent-filter>

  <meta-data
      android:name="org.chromium.default_payment_method_name"
      android:value="https://sampleapp.example/pay" />
  <meta-data
      android:name="org.chromium.payment_method_names"
      android:resource="@array/chromium_payment_method_names" />
</activity>

2.2. User agent app AndroidManifest.xml

In order to be able to interact with Android native payment apps, the user agent application declares its package visibility needs for the relevant intent filters in its own AndroidManifest.xml file:

<queries>
  <intent>
    <action android:name="org.chromium.intent.action.PAY"/>
  </intent>
  <intent>
    <action android:name="org.chromium.intent.action.IS_READY_TO_PAY"/>
  </intent>
</queries>

2.4. Claiming a method URL

The claimed payment method identifier for an Android application, app, is the value of the org.chromium.default_payment_method_name <meta-data> tag in app’s AndroidManifest.xml file.

2.5. Claiming a set of origins

The set of claimed third-party origins for an Android application, app, is created from the value of the org.chromium.payment_method_names <meta-data> tag in app’s AndroidManifest.xml file, as follows:

  1. Let paymentMethodIdentifiers be the value of the org.chromium.payment_method_names <meta-data> tag.

  2. If paymentMethodIdentifiers is not a string array, return an empty set.

  3. Let origins be an empty set.

  4. For each string identifier in paymentMethodIdentifiers:

    1. If identifier is not a valid url-based payment method identifier, go to the next iteration of the loop.

    2. Let origin be the origin of identifier.

    3. Add origin to origins.

  5. Return origins.

We need to document why this is an array of method URLs, rather than just an array of origins.

2.8. Invoking an Android native payment app

In order to invoke the native payment app, app, for a PaymentRequest request, the user agent performs the following steps:

  1. Let packageName be the Android package name for app.

  2. Let activityName be the Activity name for app.

    TODO - these name to be part of some sort of app concept

  3. Let extras be the result of creating an Android bundle for request.

  4. Create an Intent object, intent, whose:

    1. Class name is set to the combination of packageName and activityName, e.g. via Intent.setClassName.

    2. Action is set to org.chromium.intent.action.IS_READY_TO_PAY.

    3. Extras are set to extras, e.g. via Intent.putExtras.

  5. Send intent to the Android OS in such a way that the user agent will be notified on result, e.g. via Activity.startActivityForResult.

2.10. Indicating success of an invoked Android native payment app

In order for an invoked Android application, app, to indicate success back to the user agent, app performs the following steps:

  1. Call Activity.setResult with Activity.RESULT_OK and with an Intent containing:

    1. A "methodName" Intent extra, set to the string name of the method being used.

    2. A "details" Intent extra, set to a JSON string containing any payment-app specific result information.

  2. Terminate the app’s activity, e.g. via Activity.finish().

2.11. Indicating user cancel from an invoked Android native payment app

In order for an invoked Android application, app, to indicate user cancellation back to the user agent, app performs the following steps:

  1. Call Activity.setResult with Activity.RESULT_CANCEL.

  2. Terminate the app’s activity, e.g. via Activity.finish().

2.12. Indicating internal error from an invoked Android native payment app

In order for an invoked Android application, app, to indicate internal error back to the user agent, app performs the following steps:

  1. Let RESULT_INTERNAL_ERROR be equal to Activity.RESULT_FIRST_USER.

  2. Call Activity.setResult with RESULT_INTERNAL_ERROR.

  3. Terminate the app’s activity, e.g. via Activity.finish().

2.13. Creating an Android bundle

To create an Android bundle from a PaymentRequest, request, perform the following steps:

  1. Let bundle be a new Bundle object.

  2. Insert request.id into bundle with the key "paymentRequestId".

  3. Insert the title of request’s relevant global object’s associated Document into bundle with the key "merchantName".

  4. Insert request.[[details]].total.amount into bundle with the key "total".
